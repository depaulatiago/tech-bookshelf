## Summary

Functional programming (FP) is a paradigm that builds programs by composing **pure functions**. A pure function's output depends only on its input, and it doesn't change anything outside itself. Data is **immutable**, functions are **values** that can be passed around, and **side effects** (I/O, mutation, exceptions) are pushed to the edges of the program. The main payoff is code that is easier to reason about, test and combine, which matters most as a codebase grows.

## Key concepts

### Immutability

Once a value is created it never changes. To "modify" it, you create a new value derived from the old one. This removes a whole class of bugs: shared state that changes unexpectedly, especially with concurrency.

```scala
val xs = List(1, 2, 3)
val ys = xs :+ 4   // new list; xs is still List(1, 2, 3)
```

### Referential transparency

An expression is referentially transparent when you can replace it with its result without changing the program's behavior. Pure functions give you this: `add(2, 3)` can always become `5`. That lets you reason about code locally, like algebra.

```scala
def add(a: Int, b: Int): Int = a + b   // transparent

var total = 0
def addToTotal(n: Int): Int = { total += n; total }   // not transparent: result depends on hidden state
```

### Higher-order functions

Functions are values: they can be passed as arguments and returned as results. A higher-order function takes or returns another function. `map`, `filter` and `fold` replace most manual loops.

```scala
val nums = List(1, 2, 3, 4)
nums.filter(_ % 2 == 0).map(_ * 10)   // List(20, 40)

def twice(f: Int => Int): Int => Int = x => f(f(x))
twice(_ + 3)(1)   // 7
```

### Lazy evaluation

An expression is only evaluated when its value is actually needed. This avoids unnecessary work and makes infinite structures possible.

```scala
lazy val expensive = { println("computing..."); 42 }   // runs only on first use

val naturals = LazyList.from(1)
naturals.map(_ * 2).take(3).toList   // List(2, 4, 6)
```

### Thinking like a functional programmer

- Describe **what** to compute (transformations over data), not **how** to step through it
- Break problems into small pure functions and **compose** them
- Treat side effects as something to isolate, not something spread everywhere
- Model data with immutable types and let the types guide the design

### The benefits of FP

- **Easier to reason about:** no hidden state, so each function can be understood alone
- **Easier to test:** same input, same output, with no setup or mocks for state
- **Safer concurrency:** immutable data can be shared between threads without locks
- **Reusability and composition:** small generic functions combine into larger behavior

#### Can FP increase productivity?

The upfront learning curve is real, but less time goes into debugging state-related bugs and understanding what code does. Programs also tend to be shorter.

#### FP is fun

Solving problems by composing small, correct pieces gives a satisfying, almost mathematical feeling. It also changes how you think in any language.

### Scala

The book uses Scala: a JVM language that mixes object-oriented and functional programming. It has immutable collections by default, first-class functions, pattern matching and a strong type system, which makes it a practical way to apply FP in real projects.
